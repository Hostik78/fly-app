# Журнал решённых технических проблем

Сюда записываются конкретные технические открытия и грабли по этому проекту —
чтобы в следующий раз не наступать на них заново и решать похожие проблемы быстрее.
Это не идеи на будущее (те — в notes.md), а уже случившиеся уроки.

## Simple Browser в VS Code ненадёжен для dev-сервера Vite (2026-07-22)

Встроенный Simple Browser у VS Code иногда не подхватывает "живое обновление" (HMR)
от Vite и показывает закэшированную старую версию страницы, даже после реальных
изменений в коде. Признаки: пользователь видит старую вёрстку, хотя код и сборка
точно свежие (проверено скриншотом с реального dev-сервера).
**Решение**: не полагаться на Simple Browser для проверки live-изменений — открывать
обычный браузер (Chrome/Safari) на тот же localhost-адрес, либо для быстрой сверки
пересобрать проект (`npm run build`) и опубликовать статический снимок как Artifact.

## backdrop-blur сильно тормозит зум трекпадом (2026-07-22)

`backdrop-blur-*` в Tailwind — дорогой в отрисовке эффект: браузер должен пересчитывать
размытие фона при каждом кадре во время нативного zoom-жеста (пинч трекпадом/Ctrl+скролл),
из-за чего страница подвисает при масштабировании.
**Решение**: убирать backdrop-blur с элементов, которые видны во время зума
(например, панель инструментов), или заменять на сплошной/полупрозрачный фон без blur.
Также помогает `will-change: transform` на элементах, которые масштабируются.

## Вырез экрана (notch/Dynamic Island) — это данные, а не código-ветвление (2026-07-22)

Ошибка была в том, что рамка телефона рисовала одну и ту же "чёлку" для всех моделей,
включая iPhone SE — а у него никакого выреза нет вообще (кнопка Touch ID).
**Решение**: тип выреза — это поле данных у каждой модели устройства
(`'none' | 'notch' | 'dynamic-island' | 'punch-hole'`), а рендер рамки просто читает
это поле и рисует нужную фигуру (или ничего). Никакого `if (модель === 'iPhone SE')`
в коде — только один общий кусок кода, управляемый данными. Так принцип
"не изобретай логику под конкретную модель" (см. CLAUDE.md) соблюдается автоматически.

## Реальные размеры выреза экрана нельзя подбирать на глаз (2026-07-23)

Даже когда тип выреза берётся из данных (см. пункт выше), сами цифры размера/отступа
были придуманы "на глаз" (90×26px, отступ 10px) — визуально что-то похожее на остров,
но не совпадающее с реальным устройством, из-за чего вырез выглядел мелким и смещённым
вверх. Вторая ошибка: элемент выреза позиционировался `absolute` от рамки телефона
(чёрного бордера с `p-3`), а не от самого экрана (белого прямоугольника) — из-за этого
любое изменение толщины рамки сдвигало вырез относительно экрана.

**Решение**:
1. Для UI-элементов, повторяющих реальные физические устройства (вырезы экрана,
   safe area, размеры статус-бара и т.п.) — брать точные величины, а не "на вид похоже".
   Актуальные значения для iPhone 14 Pro/15/16 Pro (логическая ширина экрана 393pt):
   Dynamic Island — 126×37pt, с отступом сверху 11pt от края экрана (не вплотную).
   Классический notch (iPhone X–13) — вплотную к верхнему краю, без отступа,
   шириной порядка 160pt.
2. `absolute`-элемент выреза класть внутрь контейнера самого экрана (тот `div`,
   что и рисует белый прямоугольник с `overflow-hidden`), а не внутрь внешней рамки —
   так его положение не зависит от толщины бордера/паддинга рамки.

## Supabase по умолчанию даёт новой таблице права шире, чем указано в grant (2026-07-28)

Миграция писала `grant select, insert on public.<table> to authenticated;` и ничего
для `anon` — но на деле у обеих первых таблиц (`posts`, `profiles`) `anon` и
`authenticated` внезапно имели ВСЕ права: select/insert/update/delete/truncate/
references/trigger. Причина - это платформенный дефолт Supabase на уровне проекта
(`alter default privileges ... grant all on tables to anon, authenticated`,
настроено автоматически при создании проекта), а не что-то, что ставит конкретная
миграция - `grant` в миграции просто ничего не отнимал, только добавлял.

Опаснее всего то, что RLS-политики закрывают select/insert/update/delete по строкам,
но **`TRUNCATE` в Postgres вообще не подчиняется Row Level Security** - имея грант
`truncate`, буквально любой человек с публичным `anon`-ключом (то есть кто угодно
без входа в приложение) мог одной командой стереть таблицу целиком, несмотря на
включённый RLS и правильные политики.

**Решение**: для каждой новой таблицы, где `anon` не должен иметь вообще никакого
доступа (как в этом проекте - все действия с базой требуют входа), явно писать
`revoke all on public.<table> from anon, authenticated;` ПЕРЕД `grant select, insert
... to authenticated;` - не полагаться на то, что "я просто не написал grant для
anon, значит у него ничего нет". Проверять права после применения миграции:
`select grantee, privilege_type from information_schema.role_table_grants where
table_schema='public' and table_name='<table>';`.

## Supabase CLI: сообщения об ошибках `db push` не показывают настоящую причину (2026-07-28)

`supabase db push` при сбое SQL-выражения выводит `LegacyDbPushApplyError` с текстом
самого выражения, но БЕЗ настоящего сообщения об ошибке от Postgres (например,
"relation already exists" просто не показывается - видно только общее "Failed to
execute statement"). Так и не разобрались через саму CLI, в чём дело (после серии
`create table` под разными именами выяснилось: `public.profiles` уже существовала
в базе, создана раньше вручную через Dashboard).

**Решение**: если `db push` падает без понятной причины - подключиться к базе
напрямую через `psql` (после `brew install libpq`, бинарник не в PATH:
`/opt/homebrew/opt/libpq/bin/psql`) и проверить состояние своими глазами. Строка
подключения (Session Pooler, порт 6543, часто работает надёжнее прямого
`db.<ref>.supabase.co`, который может не резолвиться из-за IPv6-only):
`postgresql://postgres.<project-ref>@aws-0-<region>.pooler.supabase.com:6543/postgres`
(регион/ref - через `curl -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN"
https://api.supabase.com/v1/projects/<ref>`), пароль - через `PGPASSWORD=...`
переменную окружения, не в самой команде.

Также: если миграция упала на каком-то выражении, CLI откатывает ВЕСЬ файл целиком
(включая уже успешные `drop table` до места сбоя) - "успешные" по логам шаги на
самом деле не применились, если после них что-то сломалось дальше в том же файле.

## Та же ловушка с грантами, но для функций базы данных, не таблиц (2026-07-30)

Написал `revoke all on function public.count_pending_likes() from public;` перед
`grant execute ... to authenticated;` - казалось бы, ровно тот урок, что записан
выше про таблицы. Но `supabase db advisors` всё равно показал предупреждение
"anon может выполнить эту SECURITY DEFINER функцию", и прямая проверка в базе
это подтвердила: `anon` действительно имел `EXECUTE`.

Причина та же по духу, но конкретный механизм другой: `revoke ... from public`
отнимает права у псевдо-роли `public` (то, что наследуют ВСЕ роли по умолчанию),
но у Supabase есть ОТДЕЛЬНЫЕ дефолтные права, выданные `anon`/`authenticated`
напрямую по имени (не через `public`) на новые объекты в схеме `public` - и `revoke
... from public` их не трогает вообще, потому что это разные получатели гранта.

**Решение**: для функций (как и для таблиц) отзывать права по имени роли явно -
`revoke execute on function public.<fn>() from anon;`, а не полагаться на
`revoke ... from public`. Проверять после миграции: `select grantee, privilege_type
from information_schema.routine_privileges where routine_name = '<fn>';` - и
обязательно прогонять `supabase db advisors` после любой новой функции с
`security definer`, он ловит именно такие случаи.

**Уточнение (2026-07-31, на функции notify_push_webhook)**: бывает и наоборот -
право оказывается у `public`, а не у `anon`/`authenticated` напрямую (обычное
поведение Postgres: `create function` сам выдаёт `EXECUTE` роли `public`, если
явно не отозвать - это ДРУГОЙ источник гранта, чем разобранная выше особенность
Supabase). На этой функции `revoke ... from anon, authenticated` не помог -
предупреждение осталось, а прямая проверка показала грант именно у `public`.
Помогло только `revoke execute on function public.<fn>() from public;` отдельно.

Итог: источника гранта два, независимых друг от друга, и функция может
пострадать от одного, другого или обоих сразу - отзывать нужно явно **и у
`public`, и у `anon, authenticated`** каждый раз, не полагаясь, что раз в прошлый
раз хватило одного - хватит и в этот.

## DevicePreview маскировал настоящую поломку высоты экрана (2026-08-02)

`h-full` (height: 100%) на корневых div каждого экрана ничего не значит сам по
себе - проценты высоты считаются от родителя, и если хоть одно звено в цепочке
`html → body → #root` не растянуто на весь экран явно, дальше это не передаётся
(это не Tailwind-специфика, а базовое поведение CSS). В index.css такого правила
никогда не было - но это было не видно НИ РАЗУ за всю разработку, потому что
`DevicePreview` (рамка телефона для удобного превью на компьютере) всегда задавала
себе точный размер в пикселях напрямую (`style={{width: DEVICE.width, ...}}`),
а не через проценты - опираться на реальную высоту страницы вообще не приходилось.

Как только `DevicePreview` убрали из настоящей сборки (см. commit про
`import.meta.env.DEV`), сразу стал виден шов: экран приложения заканчивался на
высоте своего контента (сотня-другая пикселей), а ниже был просто цвет фона
страницы - на настоящем телефоне это выглядело бы как обрезанное наполовину
приложение.

**Решение**: `html, body, #root { height: 100%; }` явно в index.css.

**Отдельный урок по методике проверки**: пока разбирался, несколько раз проверял
через `getComputedStyle` в уже открытой вкладке браузера после пересборки -
это давало то верные, то неверные показания без явной причины, пока не понял:
нужно каждый раз открывать СОВСЕМ новую вкладку/порт (или жёстко сбрасывать кеш),
а не просто `page.goto()` на тот же самый адрес поверх уже открытой страницы -
иначе не всегда понятно, что именно видишь: свежую сборку или что-то от
предыдущей проверки в этой же вкладке.

## Сборка настоящего APK через Bubblewrap - интерактивный мастер CLI ненадёжен (2026-08-02)

Google Bubblewrap (официальный инструмент, оборачивает уже готовый сайт в
Android-приложение - Trusted Web Activity, без отдельного кода) на бумаге
работает через интерактивный мастер (`bubblewrap init`, `bubblewrap build`),
но в среде без настоящего интерактивного терминала (команды выполняются по
одной, без общего состояния между вызовами) этот мастер ненадёжен - падает
на первом вопросе (`ERR_USE_AFTER_CLOSE`) или ведёт себя непредсказуемо при
попытке подать ответы через пайп в stdin.

**Решение - обходить мастер целиком, а не бороться с ним**:
1. Конфиг JDK/Android SDK - писать `~/.bubblewrap/config.json` напрямую
   (`{"jdkPath":...,"androidSdkPath":...}`), это пропускает мастер первого запуска.
2. `twa-manifest.json` - генерировать программно через Node-скрипт, вызывающий
   `TwaManifest.fromWebManifest(url)` из `@bubblewrap/core` и `.saveToFile()`,
   вместо `bubblewrap init`.
3. Пароли от ключа подписи - передавать через переменные окружения
   `BUBBLEWRAP_KEYSTORE_PASSWORD`/`BUBBLEWRAP_KEY_PASSWORD` (нашлось через grep
   по исходнику `build.js`), а не отвечать на вопросы интерактивно.

**Другие грабли на этом же пути**:
- Встроенный автозагрузчик JDK у самого Bubblewrap в этой среде скачивал
  исходный код OpenJDK (`configure`, `Makefile`, репозиторий), а не готовую
  программу - пришлось ставить JDK 17 через Homebrew отдельно.
- Homebrew кладёt настоящий JDK на уровень глубже, чем ожидаешь:
  `/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home`, а не
  `/opt/homebrew/opt/openjdk@17/Contents/Home` - вторая версия даёт
  "JAVA_HOME is set to an invalid directory".
- Проверка пути Android SDK в Bubblewrap ищет `tools/` или `bin/` прямо в
  корне SDK (старый формат) - у Homebrew инструменты лежат в
  `cmdline-tools/latest/bin/` - помог симлинк `sdkRoot/bin ->
  cmdline-tools/latest/bin`.
- Версия build-tools, которую требует Bubblewrap, может быть новее той, что
  выглядит "последней стабильной" - нужную версию видно в исходнике
  (`grep BUILD_TOOLS_VERSION` по `@bubblewrap/core`).
- Экспортированные переменные окружения (`JAVA_HOME`, `ANDROID_HOME`) не
  сохраняются между ОТДЕЛЬНЫМИ вызовами команд в этой среде - задавать их
  нужно в каждой команде, где они нужны, заново.

Полная инструкция по пересборке - `android/README.md`. Ключ подписи
(`android/android.keystore`) - специально НЕ в git, без него будущее
обновление уже установленного на телефоне приложения станет невозможным.

## DevicePreview маскирует изменения фона body при проверке через npm run dev (2026-08-02)

При переносе дизайна "Стекло" фон страницы (`body`) поменяли с плоского цвета на
градиент - но при проверке через `npm run dev` в браузере градиент не был виден
вообще, экран выглядел просто белым. Причина не в самом градиенте (он был написан
правильно), а в том, что `DevicePreview.tsx` (рамка телефона для удобства
разработки на компьютере) сама рисует `bg-white` на внутреннем "экране" рамки
(строка с `rounded-[42px] overflow-hidden bg-white`) - это перекрывает фон body
целиком, потому что содержимое приложения рендерится ВНУТРИ этого белого блока.

**Решение**: если меняется что-то на уровне фона всей страницы (body/html), а не
внутри конкретного экрана - проверять через `npm run build && npm run preview`
(настоящая сборка, без DevicePreview - см. `import.meta.env.DEV` в App.tsx), а не
через `npm run dev`. Иначе можно ошибочно решить, что изменение не сработало,
хотя на самом деле не видно только из-за рамки предпросмотра.
