# Приватность фото: модель и порядок внедрения

Согласованная цель: владелец выбирает видимость фото. Приватное фото доступно только ему и явно выбранным людям. Совпадение не выдаёт разрешение. Блокировка в любую сторону запрещает чтение и удаляет ранее выданные разрешения. Разблокировка их не восстанавливает.

## Модель угроз

Недоверенный клиент может угадать UUID, обращаться прямо к Storage/RPC, сохранить ссылку, повторить старый JWT после выхода, подписаться на общий Realtime и одновременно менять доступ. Проверки интерфейса не считаются защитой. Уже скачанные копии и завершённые ответы отозвать невозможно.

Выбран закрытый новый бакет `profile-photos`, без клиентского SELECT/INSERT/UPDATE/DELETE и подписанных ссылок. Сервер выдаёт байты только после проверки действующей сессии и разрешения в базе, повторяя проверку после скачивания из Storage. Ответы и браузерные запросы no-store. Клиент хранит лишь временный blob URL и очищает его при выходе/смене сессии/скрытии страницы; активные фото перепроверяются. Ранее доставленные байты — уже полученная копия.

Метаданные и разрешения находятся в закрытой схеме. Публичные RPC проверяют auth.uid и auth.sessions; путь нового файла фиксирует только service_role. Новые и перенесённые фото по умолчанию приватные. Видимость «в ленте» ограничена существующим кругом видимости анкеты, блокировки проверяются отдельно.

Список блокировок возвращает только собственные записи с нейтральными полями, без живой анкеты. Общий Presence/Broadcast заменяется чтением/записью краткоживущих статусов через базу с проверкой пары при каждом запросе. На production требуется выключить публичные Realtime-каналы и отключить старые соединения, иначе старый клиент продолжит публикацию.

## Проверяемые этапы

- [ ] SQL-тесты реальных ролей PostgreSQL: владелец/посторонний/разрешение/отзыв/совпадение/оба направления блокировки/выход/подмена владельца/Storage.
- [ ] Добавочная миграция, сервер выдачи и загрузки, очистка при удалении аккаунта.
- [ ] Единый компонент фото, настройки видимости и явное разрешение в переписке; нейтральный список блокировок, безопасные статусы.
- [ ] Инструкция перехода и отдельная защищённая активация. Не применять закрытие старого бакета до готовности нового клиента и переноса файлов.
- [ ] Независимый обзор, тесты, lint, production build, браузер. Отдельно перечислить непроверенное.

## Условия выпуска

Доступ Supabase CLI на 2026-09-27 повторно отвечает 401. Ни схема, ни production не изменены. Не выпускать клиент и не активировать приватность до восстановления управляющего доступа и изолированной проверки всей цепочки Storage/Auth/API.

Перенос: остановить старые загрузки на согласованное окно обслуживания; скопировать и проверить все существующие файлы в новый закрытый бакет, сохранить журнал соответствий без публичных данных, удалить оригиналы через Storage API (не SQL). Проверить пустоту старого бакета, все старые публичные/подписанные/transform URL и CDN; при необходимости добиться очистки через поддержку Supabase. Только затем активировать серверную выдачу. До подтверждения очистки нельзя обещать приватность старых фотографий. Старые приложения требуют обновления; тихое сосуществование с публичным путём не допускается.

Следующий отдельный этап: серверные лимиты сообщений, заметок, подсказок и загрузок. В текущем api/suggest.ts нет ограничения частоты платных запросов; это подтверждённый риск, не часть защиты фото.
